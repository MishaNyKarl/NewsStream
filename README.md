# Бот наблюдения за развитием новостей

Закрытый Telegram MVP на 10 участников. Пользователь присылает ссылку или описание, подтверждает карточку сюжета и получает сообщения только при существенном развитии истории. Интерфейс на русском. Наблюдение начинается с момента создания: архивные публикации с более ранней датой не выдаются за новые события.

## Что реализовано

- URL и текст → структурированная карточка → подтверждение → PostgreSQL.
- Текущее состояние сюжета, цели наблюдения, сущности и поисковые запросы.
- Автоматические проверки раз в сутки и ручная проверка с ограничениями.
- Режим «Следить внимательнее»: одна тема на пользователя, проверки через 30 минут, 1, 2, 4, 8, 12 и 24 часа от включения, затем — обычное расписание. Выбор при подписке и в карточке, перенос с подтверждением, ближайшая проверка в МСК.
- Реальный бесплатный поиск Bing News RSS; альтернативы Google News RSS и API-провайдеры.
- Нормализация URL, хеши и сравнение похожих текстов; повторная статья не запускает повторный анализ.
- Сравнение найденных фактов с состоянием сюжета через OpenRouter, проверка JSON и ссылок на доказательства.
- Порог новизны 0.65, значимости 0.55, уверенности 0.75. Модель должна явно подтвердить существенное изменение и назвать новые факты. При отсутствии обновлений бот молчит.
- Уведомления со ссылками, «Полезно / Неважно», история последних обновлений, пауза, возобновление и удаление.
- Доступ по приглашениям, отдельный одноразовый вход администратора, статистика, журнал ошибок, демонстрационный режим.
- Кнопка «Обсудить — скоро». Полноценный чат, рекомендации, платежи и веб-панель не входят в MVP.

## Архитектура и структура

Один проект, два процесса: Telegram long polling и фоновый worker. Они используют одну базу. Домен/HTTPS для этого не нужны. База и процессы не публикуют порты наружу.

```text
app/
  main.py          запуск bot/worker
  config.py        настройки из окружения
  domain.py        проверяемые схемы ответов AI
  bot.py           Telegram UX, авторизация, кнопки
  service.py       сценарии и фильтр существенных обновлений
  monitoring.py    общая политика частых проверок для бота и будущего API
  worker.py        расписание и доставка уведомлений
  db.py            подключение к БД
  models.py        SQLAlchemy модели
  repository.py    транзакции, квоты, блокировки, история
  ai/              структурированные запросы к модели
  search/          поиск и устранение дублей
  content/         безопасное извлечение страниц
migrations/        версия схемы Alembic
tests/             автоматические проверки
docs/              инструкции тестировщикам и эксплуатация
compose.yaml       bot + worker + отдельный PostgreSQL
.env.example       перечень настроек без секретов
```

Стек: Python 3.12, aiogram 3, SQLAlchemy 2, asyncpg, PostgreSQL 16, Alembic, aiohttp/httpx, Pydantic, Docker Compose. Отдельный Redis или APScheduler не требуется: расписание хранится в БД, worker опрашивает очередь каждые 10 секунд. Lease и транзакционные блокировки защищают от одновременной обработки одной истории. Новое состояние и уведомление сохраняются одной транзакцией; доставка идёт через outbox с ограниченными повторами.

## Режим частых проверок

Расписание отсчитывается от включения режима: через 30 минут, 1, 2, 4, 8, 12 и 24 часа. Это плановое время начала: очередь и доступность источников могут задержать проверку. Сообщения по-прежнему приходят только при существенных новых фактах.

Одна тема занимает место частого наблюдения на пользователя, в том числе на паузе. Пауза останавливает проверки, но не продлевает сутки режима. Возобновление ставит ближайшую будущую контрольную точку. Выключение, удаление или окончание суток освобождает место; при переносе прежняя тема возвращается к обычному расписанию, сохраняя паузу. Для возобновлённой обычной темы первая проверка запускается сразу.

Перенос проверяет, какая тема занимала место на момент подтверждения: устаревшая кнопка не заменит другую тему молча. Повторное нажатие не перезапускает срок. Квота защищена транзакцией с блокировкой пользователя и частичным уникальным индексом PostgreSQL. Миграция `0002_intensive_monitoring` сохраняет существующие темы в обычном режиме.

После простоя выполняется одна просроченная проверка, затем ближайшая будущая; пачки пропущенных проверок нет. Ошибка частой проверки повторяется через 5 минут или в ближайшую контрольную точку, если она раньше; обычной — через 30 минут. Ручная проверка не откладывает будущую автоматическую. Общий лимит LLM остаётся 250 попыток в сутки на весь бот: частый режим использует тот же бюджет.

## API и ключи

1. Создайте бота в [BotFather](https://t.me/BotFather), команда `/newbot`, и сохраните токен в `TELEGRAM_BOT_TOKEN`.
2. Создайте ключ в [OpenRouter](https://openrouter.ai/settings/keys), пополните баланс и укажите `LLM_API_KEY`. Модель по умолчанию — `qwen/qwen3-30b-a3b-instruct-2507`. У провайдера можно дополнительно установить лимит ключа. Поддерживаемые варианты смотрите в `app/ai/client.py`.
3. Для Bing News RSS/Google News RSS ключ не нужен. Это временный источник MVP без гарантированного SLA. При необходимости выберите поддерживаемый платный провайдер поиска и заполните `SEARCH_API_KEY`.

Конфигурация OpenRouter использует JSON Schema, затем локальную проверку Pydantic. Документация: [structured outputs](https://openrouter.ai/docs/features/structured-outputs), [карточка модели](https://openrouter.ai/qwen/qwen3-30b-a3b-instruct-2507). При развёртывании Google и OpenAI вернули 403 с ограничением провайдера; Qwen оказался доступен через тот же ключ.

Секреты находятся только в `.env` на сервере, с правами `0600`. Они не входят в Git, образ Docker или архив исходников. Не включайте отладочное логирование HTTP-заголовков. При изменении `.env` перезапустите процессы через `docker compose up -d --force-recreate bot worker`.

## Запуск через Docker

Требуются Docker Engine и Docker Compose.

```sh
cp .env.example .env
# Заполните токены, сгенерируйте разные длинные случайные коды доступа.
# POSTGRES_PASSWORD и пароль в DATABASE_URL должны совпадать.
chmod 600 .env
docker compose build
docker compose up -d db
docker compose run --rm bot alembic upgrade head
docker compose up -d bot worker
docker compose ps
docker compose logs --tail 100 bot worker
```

Используйте случайный пароль из букв/цифр для БД; специальные символы в URL требуют percent-encoding. `DATABASE_URL` в Compose использует имя хоста `db`. Миграции выполняются отдельной командой до запуска обновлённого кода. Контейнеры запускают приложение от непривилегированного пользователя, с ограничениями памяти, закрытыми портами и автоматическим перезапуском. Существующие сайты на VPS не затрагиваются.

## Локальный запуск

```sh
python -m venv .venv
# Linux/macOS:
. .venv/bin/activate
# Windows PowerShell вместо предыдущей строки:
# .\.venv\Scripts\Activate.ps1
pip install -e '.[test]'
cp .env.example .env
```

Создайте отдельную базу PostgreSQL и пользователя. В `.env` укажите `DATABASE_URL=postgresql+asyncpg://USER:PASSWORD@localhost:5432/newswatch`, заполните ключи. Затем:

```sh
alembic upgrade head
python -m app.main bot
# Второй терминал:
python -m app.main worker
```

Не запускайте одновременно локальный polling и серверный polling с одним Telegram-токеном. Автотестам Telegram/OpenRouter-ключи не нужны.

## Доступ и команды

Для первого владельца откройте `https://t.me/BOT_USERNAME?start=admin_ADMIN_CLAIM_TOKEN`. Используется значение из `.env`. Ссылка выдаёт права только до появления первого администратора. Храните её отдельно и не пересылайте тестировщикам. Альтернатива — заранее заполнить `ADMIN_TELEGRAM_IDS` числовым Telegram ID.

Тестировщики входят по `https://t.me/BOT_USERNAME?start=invite_INVITE_CODE`. `/admin` показывает эту ссылку. Максимум 10 тестировщиков плюс администратор; приглашение не делает пользователя администратором. Уже принятые участники сохраняют доступ при смене invite-кода. Для более строгого первоначального допуска очистите `INVITE_CODE` и задайте `ALLOWED_TELEGRAM_IDS` через запятую. Отзыв доступа у уже принятого участника в UI пока не реализован.

Основные действия:

| Действие | Как выполнить |
|---|---|
| Создать наблюдение | Отправить URL или текст, нажать «Следить» |
| Свои сюжеты | `/watching` |
| Ручная проверка | Кнопка в карточке или `/check_now ID` |
| Пауза / возобновление | Кнопки карточки |
| Удаление | «Удалить», затем подтверждение |
| История | Кнопка истории в карточке |
| Метрики | `/admin`, только администратор |
| Ошибки | `/admin_errors`, только администратор |
| Демо | `/demo_update ID`, только администратор при `DEMO_MODE=true` |

Демо создаёт **явно помеченное тестовое уведомление** и не меняет реальное состояние истории. Чтобы его включить: измените `.env`, выполните `docker compose up -d --force-recreate bot worker`, создайте активное наблюдение и вызовите `/demo_update`. После демонстрации верните `DEMO_MODE=false`.

## Лимиты и расходы

По умолчанию: 10 наблюдений на человека, проверка раз в 24 часа, 3 поисковых запроса, 4 результата на запрос, максимум 6 новых источников для одного анализа. Не больше 5 ручных проверок в день на пользователя с паузой 120 секунд между ними. Лимит действует на пользователя и не сбрасывается удалением истории.

Общий лимит — 250 попыток обращения к LLM в сутки UTC, включая повторные запросы после ошибочного ответа. После исчерпания бот не отправляет запросы до следующего дня. Фактические токены и приблизительная стоимость учитываются в БД; тариф задаётся через `LLM_INPUT_COST_PER_MILLION`/`LLM_OUTPUT_COST_PER_MILLION`. Это **оценка**, а не банковский лимит: окончательные списания видны в OpenRouter. При смене модели обновите тариф и отдельно задайте денежный предел у провайдера. Поисковые RSS-запросы не имеют платы за вызов.

## Ограничения MVP

- Новостные RSS не являются полноценным web-search API: часть тем, языков и публикаций может отсутствовать, индексирование запаздывает. Google-ссылки могут требовать JavaScript; Bing иногда ведёт на агрегатор MSN. Платные стены и заблокированные сайты не обходятся.
- Если исходная ссылка не читается безопасно, бот просит прислать текст. При проверке может использовать доступный заголовок/фрагмент, явно отмеченный как неполный. Такие источники оцениваются консервативно.
- Семантический фильтр вероятностный. Оценки модели не являются калиброванной вероятностью достоверности; возможны пропуски и ложные уведомления. Обратная связь нужна для оценки качества.
- Материалы с известной датой до создания наблюдения исключаются. Если дата неизвестна, корректность временного вывода зависит от текста источника и модели.
- Уже обработанный URL не перечитывается на каждом цикле: обновление статьи по тому же адресу может быть пропущено. Похожие тексты сравниваются с последними 100 источниками; все старые URL всё равно исключаются.
- Telegram не имеет идемпотентного ключа отправки. После редкого сбоя между доставкой и записью статуса возможен повтор уведомления. После пяти неудачных попыток запись остаётся в БД для диагностики. Пауза/удаление проверяются перед отправкой, но уже отправленное сообщение не отзывается.
- Хранятся краткие извлечённые тексты до 7500 символов, не полный архив сайтов. Удаление наблюдения удаляет его источники и историю, обезличивает связанное использование API. Имя/ID пользователя остаются для закрытого доступа.
- Нет внешнего Sentry/PostHog, интерфейса отзыва доступа, платежей, чата и персональных рекомендаций.

## Переход к Telegram Mini App

Для Telegram Mini App можно использовать текущие `BotService`, `Repository` и worker: браузер только отображает темы и передаёт действия, расписание продолжает работать на сервере после закрытия приложения. Минимальные экраны — список тем с выделенной частой темой, добавление/подтверждение, карточка с режимом/паузой/ручной проверкой, история с источниками и оценкой полезности. Сохраняются приглашения и закрытый доступ; административная статистика, ошибки и демо доступны в отдельном экране. Полноценный AI-чат сейчас является заглушкой и в перенос имеющихся функций не входит.

Плановая оценка одного разработчика: 24–40 часов, примерно 3–5 рабочих дней. HTTP API и вход через Telegram — 6–10 ч, основные экраны — 8–14 ч, административные сценарии — 4–6 ч, проверка на телефонах и развёртывание — 6–10 ч. Это оценка при использовании текущего backend и минимального оформления. Понадобятся домен с HTTPS и проверка доступной памяти VPS под дополнительный процесс API. Расширение продукта и полноценный чат оцениваются отдельно.

Приложение открывается кнопкой меню бота, учитывает тему и безопасные отступы Telegram. Backend проверяет подпись `initData`, свежесть `auth_date`, закрытый доступ и принадлежность каждой темы пользователю; ограничения не переносятся на клиент. [Официальная документация Telegram Mini Apps](https://core.telegram.org/bots/webapps).

## Следующие 5 улучшений

1. По результатам 10 тестировщиков собрать размеченный набор «повтор / развитие» и настроить пороги по измеренным ошибкам.
2. Подключить стабильный search API и приоритет официальных первоисточников.
3. Отслеживать изменения уже известных страниц и версии документов.
4. Добавить редактирование целей/частоты наблюдения, отзыв доступа и выгрузку данных в админ-режиме.
5. Добавить обсуждение истории с цитированием её состояния, источников и хронологии.
