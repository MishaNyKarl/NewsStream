# Аналитика теста NewsStream

Раздел админки **«Аналитика продукта»** (`/analytics`) объединяет поведение и расходы. Выберите даты по МСК, при необходимости Telegram ID. Администраторы исключены по умолчанию. CSV открывается в Excel: UTF-8 с BOM, разделитель `;`. В нём одна строка на пользователя, границы периода и начало наблюдений.

## Что измеряем

| Показатель | Значение |
| --- | --- |
| Активный пользователь | Хотя бы одно принятое сообщение или нажатие кнопки. Фоновая проверка, отправка уведомления, блокировка не считаются посещением. |
| DAU / WAU / MAU | Уникальные действовавшие за 1 / 7 / 30 календарных дней до последнего дня отчёта включительно. Текущий день может быть неполным. |
| Частота | Число действий, активных дней и сессий по каждому пользователю; средний DAU / MAU по наблюдаемым дням последнего 30-дневного окна. |
| Сессия | Цепочка действий с перерывами менее 30 минут. Перерыв ровно 30 минут начинает новую сессию. |
| Наблюдаемая длительность | От первого до последнего действия внутри периода. Для одного действия неизвестна. Это не экранное время. Открытые и обрезанные границей сессии отмечены. |
| Время до возврата | От последнего действия предыдущей сессии до первого следующей; медиана. Для контекста читаются ещё 30 дней до начала периода. Более ранние интервалы неизвестны. |
| D1 / D7 / D30 | Действие ровно в соответствующий календарный день после регистрации по МСК. Только новые регистрации после начала сбора и внутри выбранного периода. В знаменатель попадают лишь пользователи с полностью закончившимся целевым днём. |
| Воронка | Регистрация → отправка новости → готовая карточка → включение наблюдения → доставка развития → оценка «полезно». Считается последовательно по времени и пользователю, может включать разные новости. |
| Активация | Медиана времени от регистрации до включения наблюдения среди дошедших до этого этапа последовательной воронки. |
| Уведомления | Успешные и неуспешные доставки, ручные паузы/возобновления, автоматические паузы при запрете доставки, блокировки/разблокировки, изменения оценок. |
| Использование функций | Отправка, обработка, откладывание и удаление новостей, наблюдения, интересы, частый режим, ручные и фоновые проверки. |

Начало сбора — время установки миграции. Пропуски при остановке бота или сбоях телеметрии не восстанавливаются. Старые `last_seen_at` не превращаются в историю визитов. Отсутствие действий не доказывает уход. Удержание на маленькой выборке оценивайте вместе с размером знаменателя.

Обычное открытие чата, прочтение и отключение звука Telegram боту не сообщает. `my_chat_member` в личном чате сообщает блокировку/разблокировку; запрет доставки учитывается отдельно, поскольку он не доказывает конкретное действие пользователя. [Telegram Bot API — Update](https://core.telegram.org/bots/api#update).

## Экономика

Новые LLM-ответы сохраняют `cost_source`, `currency`, nullable `actual_cost`, `request_id`. Общий ID объединяет LLM-попытки одного анализа новости или одной проверки. Ошибочные ответы также учитываются; резерв лимита не является отдельной оплаченной операцией.

- `provider / USD`: конечная неотрицательная сумма из ответа. Известный ноль сохраняется как ноль. OpenRouter использует USD; другие совместимые API должны явно вернуть `currency=USD`.
- `estimate / USD`: расчёт по токенам и настроенным ставкам на момент вызова при отсутствии стоимости в ответе.
- `unknown`: старые записи, неизвестная валюта, некорректная сумма или отсутствующая информация. Неизвестный ноль не означает бесплатный вызов.

Основание: [OpenRouter Usage Accounting](https://github.com/OpenRouterTeam/docs/blob/main/cookbook/administration/usage-accounting.mdx), [валюта кредитов OpenRouter](https://openrouter.ai/support/). Поле `estimated_cost` сохраняется для совместимости; суммы трёх категорий не складываются как подтверждённый счёт.

Показатели на активного пользователя и доставленное развитие делят известную часть LLM-расходов выбранной группы за период на соответствующий знаменатель. Они включают фоновую работу, не включают VPS, привлечение, комиссии, налоги и труд. Обезличенные вызовы показаны отдельно и не распределяются на пользователей. Запрос на границе периода может попадать в отчёт лишь частично. При удалении темы связи её расходов обезличиваются, поэтому сумма по пользователям может отличаться от общей.

Для сценарной цены используйте существующий калькулятор: расходы сервера и прочие затраты + нагрузка → цена и безубыточность. Реальные CAC, LTV, доход, отток платных подписок и конверсия в оплату потребуют журнала платежей и источников привлечения; сейчас они неизвестны и не рассчитываются из вымышленных значений.

## Данные и точность

`product_events` хранит только Telegram ID, тип из конечного словаря, время UTC и хеш ключа дедупликации. Нет текста сообщений, URL, приглашений, произвольного callback payload или ID темы. Бизнес-события добавляются в той же транзакции, что и изменение. Повторы Telegram-сообщений/кнопок дедуплицируются; одинаковая повторная оценка не добавляет событие. Сбой записи взаимодействия логируется по типу исключения и не блокирует бота. Демо-уведомления и их оценки исключены из продуктовых доставок/оценок; расходы на демо могут входить в LLM-затраты.

Удаление темы оставляет грубую историю действий без привязки к содержимому. Удаление пользователя из БД обнуляет его ID в событиях. Автоматической очистки истории нет: это данные теста, доступные только администратору. При необходимости удаления пользовательской аналитики нужно отдельно удалить его записи, а не только тему.

Админка только читает БД. Выборка ограничена 25 000 поведенческих событий и 25 000 LLM-ответов, 10 000 пользователей, таймаутом 15 секунд; при превышении предлагает сузить период/пользователя, а не выдаёт обрезанные показатели. Таблица пользователей имеет страницы по 50; CSV содержит всю выбранную группу. Последние сессии и запросы показаны по 50. Для более крупного теста понадобится отдельная агрегирующая аналитическая БД.

## Включение при очередном релизе

1. Сохранить штатную резервную копию. Применить `alembic upgrade head` из нового образа до запуска новых bot/worker/admin. Ревизия `0007_product_analytics` добавляет таблицы и колонки, старые суммы остаются `unknown`.
2. Миграция автоматически выдаёт SELECT на новые таблицы существующей PostgreSQL-роли `newswatch_admin`. Для отдельной установки после миграции доступен `admin_ops/analytics_grants.sql`; если роль называется иначе, адаптировать имя. Роль не создаётся, права записи не выдаются.
3. Обновить bot, worker и admin через штатный release pipeline. Админка не применяет миграции сама. Версия БД и код должны совпадать.
4. Под тестировщиком выполнить `/menu`, отправить новость, включить наблюдение, поставить на паузу. Проверить события и фильтр ID в `/analytics`, исключение администраторов, скачивание CSV. Блокировку проверять отдельным тестовым аккаунтом. Проверить логи на `Product analytics` и доступность новых таблиц для read-only роли.
5. После первого LLM-вызова убедиться, что `request_id` заполнен, источник стоимости виден; неизвестная стоимость допустима, ноль не подставлять. Сверить небольшую выборку с кабинетом провайдера.

Сбор начинается после запуска обновлённого бота/worker. Миграция без обновления процессов не включает телеметрию. Откат кода совместим с дополнительными таблицами; не выполнять downgrade на накопленной истории без отдельного сохранения данных.
